## 1. 三端架构设计

### 1.1 核心问题：C/B/S 三端是在同一个小程序吗？

**不是。** 三端拆分为 **3 个独立前端 + 1 个共享后端 + 1 个运营后台**，原因如下：

| 考量维度 | 合并方案（一个小程序） | 拆分方案（推荐） |
|----------|----------------------|-----------------|
| 用户体验 | 功能堆砌，界面臃肿，C端用户看到采购功能会困惑 | 各端功能聚焦，体验极简 |
| 审核上架 | 功能混杂，微信审核难通过 | 各自独立审核，风险隔离 |
| 迭代速度 | 牵一发动全身，改 C 端可能影响 B 端 | 各端独立发版，互不影响 |
| 性能 | 包体大、加载慢 | 按需加载，首屏极快 |
| 账号体系 | 需要用户选角色，流程复杂 | 注册即明确身份，零摩擦 |

### 1.3 三端共享与隔离

| 模块 | C端 | B端 | S端 | 管理后台 |
|------|-----|-----|-----|----------|
| 用户账号体系 | 微信授权+手机号 | 微信授权+手机号+营业执照 | 手机号+企业认证 | 账密登录 |
| 菜品数据库 | 只读(查看配方) | 读+引用(组菜单) | 关联(绑定食材) | 读写(增删改审) |
| 推荐算法 | 个人口味推荐 | 商家选菜推荐 | 热销食材推荐 | 算法配置 |
| 订单系统 | C端食材订单 | B端采购订单 | 接单+发货 | 订单监控 |
| 支付 | 微信支付(用户付) | 微信支付/对公转账 | 提现/结算 | 财务管理 |
| 内容社区 | UGC发布+浏览 | 浏览(了解C端偏好) | 不涉及 | 内容审核 |
| 数据分析 | 个人饮食报告 | 经营分析报表 | 销售数据看板 | 全局数据大盘 |

### 1.4 统一账号体系

三端独立注册，但底层共用 `users` 表，通过 `user_type` 区分角色。支持一个手机号绑定多个角色（例如餐饮老板既是 B 端用户，在家做饭时也是 C 端用户）。

```
用户注册流程：
  C端：微信授权 → 手机号验证 → 选口味偏好 → 进入首页
  B端：微信授权 → 手机号验证 → 填写店铺信息(+营业执照) → 审核 → 进入工作台
  S端：手机号注册 → 企业信息认证 → 上传资质 → 审核 → 进入管理后台
```

## 8. 推荐算法设计

### 8.1 推荐引擎架构

```
┌─────────────────────────────────────────────────┐
│                推荐引擎 (Python)                  │
│                                                   │
│  ┌─────────────┐  ┌─────────────┐  ┌───────────┐│
│  │ 时令因子计算 │  │ 口味匹配模型│  │ 协同过滤  ││
│  │             │  │             │  │           ││
│  │ · 节气映射  │  │ · 口味向量  │  │ · 用户相似││
│  │ · 气温关联  │  │ · 城市偏好  │  │ · 物品相似││
│  │ · 食材季节  │  │ · 个人档案  │  │ · 矩阵分解││
│  └──────┬──────┘  └──────┬──────┘  └─────┬─────┘│
│         │                │                │      │
│         ▼                ▼                ▼      │
│  ┌─────────────────────────────────────────────┐ │
│  │            多路召回 + 排序融合                │ │
│  │                                             │ │
│  │  Score = w1×时令分 + w2×口味分 + w3×协同分   │ │
│  │          + w4×热度分 + w5×新鲜度             │ │
│  └──────────────────────┬──────────────────────┘ │
│                         │                        │
│                         ▼                        │
│  ┌─────────────────────────────────────────────┐ │
│  │        业务规则过滤 + 多样性打散             │ │
│  │  · 过敏原过滤  · 菜系多样性  · 去重          │ │
│  └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
```

### 8.2 C端推荐逻辑

**输入：** 用户ID、城市、当前日期

**处理步骤：**

1. **时令召回**：根据当前节气+城市气候，从菜品库中筛选当季菜品
2. **口味匹配**：计算用户口味向量与菜品口味向量的余弦相似度
3. **协同过滤**：找到相似用户最近收藏/做过的菜品
4. **热度加权**：结合本城市近7天的搜索/收藏热度
5. **多路融合**：加权求和得到最终推荐分数
6. **规则过滤**：去除过敏食材菜品、近7天推荐过的菜品
7. **多样性打散**：确保推荐列表中菜系不重复、难度分布均匀

### 8.3 B端推荐逻辑

**输入：** 商铺ID、目标城市、菜系偏好、预算范围

**处理步骤：**

1. **菜系筛选**：按指定菜系过滤菜品库
2. **城市适配**：加载目标城市口味偏好模型，计算菜品适配度
3. **成本约束**：根据食材实时市场价计算成本，过滤超预算菜品
4. **C端热度加权**：利用 C 端用户在该城市的搜索/收藏数据作为菜品受欢迎程度指标
5. **菜单组合优化**：用贪心算法+约束满足，生成凉菜/热菜/汤/主食的最优组合
6. **毛利优化**：在满足口味的前提下，优先推荐毛利率高的菜品
